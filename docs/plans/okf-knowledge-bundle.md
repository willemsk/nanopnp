# The knowledge base as an Open Knowledge Format bundle — evaluation and decisions

**Status: decided, not planned.** Written 4 October 2026. This note is the input to the Phase 4 work
package that §8.2.6 F6 schedules after the modularity report and before the user-testing protocol.
It is not a work-package plan. `/phase-plan 4` puts the open questions at the end to the author and
lists the package as provisional behind the modularity report (F3); `/phase-plan amend` gives it its
identifiers once that report has merged, and `/wp-plan` writes its brief. `SPECIFICATION.md`
governs.

## What OKF is

The Open Knowledge Format, v0.2, is a directory of Markdown files with YAML frontmatter, one
*concept* per file. Only `type` is required. Optional families record provenance (`sources`, each
with a stable `id` that a claim cites by footnote), trust (`generated` and `verified`, each a
`{by, at}` with an actor `<producer>/<version>`, `human:<id>` or `process:<id>`, from which a
consumer derives a tier: unverified, machine-confirmed, human-reviewed), and lifecycle (`status`,
`stale_after`). `index.md` and `log.md` are reserved. *Attested Computations* tie a value to a
sanctioned computation and a deterministic attester.

- The canonical home is `GoogleCloudPlatform/open-knowledge-format`; the `okf/` directory of
  `GoogleCloudPlatform/knowledge-catalog` is a frozen snapshot of it. The two `SPEC.md` files are
  identical at v0.2 (canonical repository last changed 21 August 2026).
- Apache-2.0. There is no validator package; the reference agent depends on Google ADK and
  BigQuery, and is not a dependency here.
- v0.1 to v0.2 broke two fields, so the version the bundle targets is pinned and declared
  (`okf_version: "0.2"` in the root `index.md`).

## What the knowledge base is today

Measured at `81ec896`: ten files and 5,666 lines, with 88 `##` sections and 114 `###`
subsections. There are 193 `[tested]` and 53 `[verified]` markers, and **4 of the 193 tested
claims name the test that backs them**. At least 28 tested claims in `07` describe a library's
behaviour, which an upgrade in `uv.lock` can silently falsify. The repository cites the base 439
times as `.knowledge/0N §x`: 133 at one level, 67 at two and 19 at three. The documentation site
renders it verbatim (§8.1, the documentation track; `docs/scripts/generate.py`).

OKF's motivation, provenance, trust and freshness, is this base's own. The base already exceeds it
in places: the VER tests attest the published numbers on every push, which is stronger than OKF's
runtime attestation, so Attested Computations are not adopted. What OKF exposes is the gap above:
"verified by running code" that names no code, and library facts with no expiry.

## What the package SHALL check

One Tier-1 test, given a VER identifier by the plan, refuses:

1. a concept without parseable frontmatter or a non-empty `type` (OKF §11), and a reserved
   `index.md` or `log.md` out of form;
2. a `.knowledge/` citation anywhere in the repository that resolves to no concept, or to no
   heading in it, under the same slug rule the documentation build uses;
3. a `[tested: …]` naming a test `pytest --collect-only` does not collect, and a bare `[tested]`;
4. a `verified` list that differs from the set of the concept's inline tests;
5. a `tested_with` version older than the one `uv.lock` resolves;
6. a footnote label that is no `sources[].id` of its concept.

## Open for the package's plan

These went to the author through `/phase-plan 4` on 5 October 2026 (`SPECIFICATION.md` §8.2.7).
Question 1 is settled by G3: two packages, joined by a committed list of unbacked claims that may
only shrink. Question 2 is settled by G8: a test where the arithmetic can be executed, and
otherwise `[verified]` with its source footnote under `process:arithmetic`. Questions 3 to 7 are
left to the bundle package's `/wp-plan` (G9). The text below is the questions as they were put.

1. **Size and split.** K6 means up to 189 new tests (fewer where an existing test already covers a claim unnamed), some `slow`, on top of a mechanical
   restructure and 439 citation rewrites. One package, or two (the bundle and its checks, then the
   backfill)? The §7.6 NOTE's four levers bound what the new tests may cost the push gate.
2. **The `[verified]` claims.** Arithmetic checks have no test node id. Each one could get a
   test (consistent with K6), or be recorded under a `process:arithmetic` actor.
3. **Each file's preamble** (the text before its first `##`). It could become an `overview`
   concept, because an OKF `index.md` holds only a listing.
4. **`00-index.md`.** It could become the root `index.md` (listing plus `okf_version`), with the
   five traps, the conventions, the provenance and the author rulings as concepts. `CLAUDE.md`'s
   "read `.knowledge/00-index.md` first" moves with it.
5. **`type` vocabulary**, for example `Physics`, `Erratum`, `Author Ruling`, `Numerics`,
   `Library Behaviour`, `Benchmark`, `Reference Settings`, `Background`. It is closed and checked,
   or open as OKF allows.
6. **`log.md`**: whether to keep one, given that git already holds the history and `.knowledge/`
   carries no project status.
7. **The documentation site**: `generate.py` recursing over the bundle, the navigation generated
   from the `index.md` files, and frontmatter rendered as page metadata under `mkdocs build --strict`.
